# Backend

The "backend" in Siegu is **one Rust facade** — `crates/siegu-core/src/rpc.rs::dispatch`
— plus thin transport adapters for each platform. Every frontend (desktop Tauri,
the `siegu-cli web` host, the WebRTC guest) reaches the same code, so behavior (and
authorization) is identical everywhere.

## The facade: `dispatch`

```rust
pub fn dispatch(ctx: &RpcContext, name: &str, payload: &Value) -> Result<Value, String>
```

- `ctx` carries the library **mode** (`ShareMode`), the `config_path`, and an
  optional live ML worker reference (`Option<&MlContext>`).
- The catalog (`rpc_catalog.rs`) drives tier gating: a guest at `ro`/`rw` is
  rejected from `owner` commands; ML arms require a worker context and are
  `ml`-gated.
- Commands implemented in `dispatch` delegate to shared helpers in `library.rs`
  (reads/writes/counts) or `ml_commands.rs` (`try_send`-based, so `dispatch`
  never blocks on the worker queue).

## Transport adapters

| Frontend | Adapter | Notes |
|----------|---------|-------|
| Desktop / mobile (Tauri) | `src-tauri/src/commands/*.rs` | thin `#[tauri::command]` wrappers; each `do_*` helper delegates to a `siegu_core` helper or calls into the ML worker. |
| Web host (browser) | `crates/siegu-cli/src/web.rs` | serves the static SPA and bridges `POST /rpc` → `dispatch` under the bearer token. |
| Guest (WebRTC) | `crates/siegu-core/src/mesh.rs` | `CommandRequest` / `CommandResponse` messages; guest principals are always `ml: None` and capped at `rw`. |

The contract the adapters share is `shared/generated/rpc-commands.ts`
(committed, generated by `build.rs`, drift-guarded).

## Capability / authorization

Authorization is **entirely server-side** in `dispatch` — frontends never branch
on mode.

| Principal | `ShareMode` | Effect |
|-----------|-------------|--------|
| Desktop user | `Owner` | everything, incl. ML |
| `siegu-cli web` bearer with `--owner-mode` | `Owner` | everything incl. ML (live worker started) |
| web / WebRTC bearer (default) | `ro` / `rw` from `--share-mode` | read, or read+write; never ML |
| guest (code+token) | capped at `rw` | read+write; never `Owner`, never ML |

Key rules (pinned by `ml_sec_tests`):

- No `--owner-mode` → web `/rpc` bearer stays at `--share-mode` with `ml: None`.
- `--owner-mode` implies `rw`; `--share-mode` then caps only guests.
- No loopback-only auth, no accounts. `Owner` == token holder at its own host's `/rpc`.

## Tauri shell details

- Entry: `src-tauri/src/main.rs`, setup in `src-tauri/src/lib.rs`.
- Managed state: `WebRtcState`, `ScanState`, `MdnsState`, `ShutdownState`,
  `MlContext` (ML worker queue), `MediaServerState`.
- Command wrappers live in `src-tauri/src/commands/` (albums, config,
  directories, geocode, indexing, logging, models, people, photos, scan,
  search, signalling, sync, wallpaper). Each delegates to `siegu_core` —
  there is no duplicated business logic in Tauri.
- Events bridge: `tauri_sync_event.rs` maps `SyncEvent` → Tauri events
  (`scan-progress`, `indexing-progress`, `peer-connected`, `photo-received`, …).

## Adding a command (backend)

1. `rpc_catalog.rs`: add `spec("new_cmd", Tier::…, stringify, &["arg1"])`.
2. Implement shared logic in `library.rs` (or `ml_commands.rs`).
3. Add the `dispatch` arm in `rpc.rs`.
4. If the desktop path needs a Tauri command, add a thin wrapper that delegates
   to the same helper.
5. Regenerate + test: `cargo build -p siegu-core`, `cargo test -p siegu-core --lib`
   (drift guard + facade tests must pass).

## Error handling

`SieguError` (7+ variants: `Database`, `Io`, `Network`, `Config`, `Model`,
`Scan`, `Sync`, `Shutdown`) maps to user-facing strings at the IPC/HTTP/WebRTC
boundaries. `dispatch` returns `Result<Value, String>` with tier-violation errors
that tell the caller what mode would allow the command (e.g. the
`--share-mode rw` hint enforced in the E2E driver).
